# Parked-Function Issue Catalog

This folder documents **why** certain functions in the THUG2 (G2TE52) GameCube
decomp are parked (cannot be byte-matched yet). **One document per distinct
root-cause issue** — a single issue may cover many functions, and a single
function may be affected by more than one issue.

## Background (read this first)

- **Game:** Tony Hawk's Underground 2, GameCube build `G2TE52` (`orig/G2TE52/sys/main.dol`).
- **Compiler:** SN Systems ProDG `ngccc.exe` (a GCC 2.95.2 derivative) — versions
  3.5 / 3.5b140 / 3.7 / 3.8.1 / 3.9.3, invoked as `-O2 -G0 -mcpu=750 -fno-common`.
  Since M5.0 the project builds with **ProDG 3.9.3** (`2.95.3 SN BUILD v1.76`),
  which is byte-identical to 3.7 for non-PS code AND has full paired-single
  support (`__ps_t` + `-mps-float` per-object, plus the SNAPS `__builtin_ps_*`
  intrinsics — see issue 06 M5.0h).
  **Version-swap caveat (Day-0 A/B, cross-clone):** Sims2DECOMP (same ProDG
  family, GC build Sep 12 2005) A/B-tested all four installed ProDG
  point-versions (3.5–3.9.3) on 609 functions with zero codegen flips —
  point versions are codegen-identical. Hypotheses of the form "try
  3.8.1/3.7/3.5" or "point-version difference" in any doc below are
  DEAD ENDS; the remaining levers are source shape, per-object flags, or
  the SNAPS intrinsics. The game's own compiler may still have differed
  from all five installed builds, but that difference is NOT a point
  version — it would be a distinct SN build.
- **Toolchain:** dtk-template (splits.txt, configure.py, mwldeppc GC/1.3.2 linker),
  objdiff for byte-comparison, m2c (decomp.me) for automated draft C generation.
- **Cross-clone reuse (2026-08):** three local ProDG-family decoMPs hold
  transferable assets - `~/ai/nfsmw` (NFS MW GC, same
  compiler family, full SDK symbol map with sizes, SNAPS + OSFastCast
  headers, era-authentic game flags `-O1 -G0 -mps-nodf` + scheduling ON),
  `~/ai/Sims2DECOMP` (The Sims 2 GC, largest ProDG
  matching corpus: 9,657/18,458 fns, 10,967 files with `// FLAGS:`
  overrides, quirk encyclopedia in `docs/tracking/walls.md`), and
   `~/ai/crashwoc` (Crash WoC GC, GCC 2.95.2/ProDG 3.5 -
   same compiler generation as THUG2's 3.9.3, C project, ~36% matched,
   full AI-tooling suite). The crashwoc tooling-transfer plan was
   executed/retired 2026-09-10 and removed: decl-permute tried with
   zero effect (item 10 below), flag-knob gaps closed as codegen-inert;
   the `--flag-sweep`/`--combos 2` harness itself remains unbuilt
   (automation only — spec: `~/ai/crashwoc/tools/ai_flag_sweep.py`,
   ladder: this background).
  Scheduling-flag priority for
   walls (Sims2 corpus evidence): **default flags FIRST**, then
   `-fno-schedule-insns` alone (~94% of their flagged files - never
   auto-pair it), then volatile-store source casts, then
   `-fno-peephole` (register-swap walls), then the `-fno-sched-spec`
   `-fno-sched-interblock` pair (THUG2-proven in AGENTS.md §4r - NOT
   Sims2-proven; their matched corpus never used it). CORRECTED 2026-08:
   `-fno-schedule-insns2` alone made things WORSE in Sims2 (their r11/r9
   coloring wall cracked by REMOVING insns2 from defaults) - treat it as
   a removal-tool unless THUG2's own re-proven cases apply (§4p recipes
   48/49: call-site order / arg0-home). Their `-O1 == -O2` for tested
   shapes. Sims2's technique catalog (var-declaration-order → callee-
   saved reg assignment, volatile-store pinning, `void *zero_p`
   separator, retptr struct-returns, sub-object pointer forcing) maps
   onto several parks here. **crashwoc automates the decl-order recipe**
   (`ai_decl_permute.py`), but the THUG2 port is RETIRED: 2026-08-23
   720-perm sweeps had ZERO effect on m2c-shaped bodies (technique-table
   item 10 below) — do not build `--decl-permute`, do not re-grind decl
   order on these classes.
   Their `ai_flag_sweep.py` harness (per-object flag sweeps +
   `--combos 2` pairwise with auto-score) remains unbuilt; its three
   candidate knobs (`-fno-move-all-movables`,
   `-fno-reduce-all-givs`, `-fno-caller-saves`) were probed 2026-08-23
   and proven codegen-inert, so only automation value remains.
- **Workflow:** functions are "parked" when no source form reproduces their exact
  bytes. Their best-guess C lives inert in `src/wip/fn_XXXXXXXX.c` (never
  compiled; the DOL stays byte-identical). See `AGENTS.md` §4g/§4m for the loop.
- **Important caveat:** the parked set is a *moving target*. Several issues
  documented as "unreproducible" in early milestones (e.g. the `subfic/adde`
  bool idiom, r13/SDA reads, `or.`-vs-`cmpwi` tests) were **later matched** —
  the classifier's verdict is not the arbiter; compiling the draft is. Re-check
  `src/` vs `src/wip/` before assuming anything below is still parked.

## 2026-09-20 — POOL DRIFT: a draft's notes can describe a body that no longer exists

Before re-attacking any parked draft, **score the file and compare that number
with the percentage in its own header**. A non-trivial share of `src/wip`
carries a body that was rewritten *in place* by an automated pass which kept
the worse result, while the header notes stayed put. Two passes are responsible:

1. **The struct-ification sweep.** It rewrites `void *` parameters/locals into
   `Unk_XXXXXXXX *` and `s32 sp8` + `(Unk_59AB5482 *)&sp8` member access into
   `Unk_59AB5482 sp8` with direct `.unk0xN` reads. This is **not** codegen
   neutral: the struct form changes store order (declaration order of the
   members / `[4]` vs `[8]`), register classes and frame slots, and it can cost

   writes the winning permutation back even when every permutation is worse, so

so a genuine later improvement is never reverted.
